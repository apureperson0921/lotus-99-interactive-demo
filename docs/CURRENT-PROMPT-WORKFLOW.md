# 当前互动故事 Prompt Workflow

## 1. 实际运行链路

```text
剧情卡 + NPC Persona + 玩家契约 + 锁定开场 + 文风
  → Prompt 1：StoryPackage（一次性故事编剧）
  → Prompt 2：RuntimePackage（一次性运行编译）
  → 后端保存 session / runtime state
  → 玩家身份或本轮言行
  → Prompt 3：8—12 个可见事件组成电影探索场景块 + 2 个玩家选项（每轮调用）
  → 后端提交合法状态变化、判断段落/章节完成、触发图片/音频/视频
  → 下一轮
```

Prompt 1 和 Prompt 2 每个新故事会话原则上各运行一次；逐轮成本与文风质量主要由 Prompt 3 决定。当前 demo 的快速启动可使用预编译 RuntimePackage，跳过在线生成 Prompt 1/2，但它仍应当是同一套契约的产物。

实际、逐字、可执行的 Prompt 1/2/3 源码位于 `app/workflow-prompts.ts`。本文件解释其职责与本轮测试形成的规则，不另复制一份容易失去同步的 Prompt。

## 2. Prompt 1：故事编剧与 StoryPackage

输入：

- 完整剧情卡；
- 已选 NPC Persona；
- 玩家独立参与契约；
- 可选的锁定开场、章节规划、初始选项和随机发言；
- 完整文风配置。

本轮测试后形成的核心规则：

1. 区分不可改的 `source canon` 与允许补足的 `authored_enrichment`。允许补人物生活、动机、关系和因果，但补充内容必须显式进入事实目录，Prompt 3 以后不得继续临时发明人物过去。
2. 玩家是独立角色，不得替代任何 NPC 的戏剧功能；玩家身份、言行、情绪和决定只能由玩家建立。
3. 锁定开场逐字保留，避免模型重写开场后出现翻译腔、重复信息或提前剧透。
4. 所有事实、关系、秘密和揭示条件使用稳定 ID；`known_by` 只代表角色私下知道，不代表可以公开说。
5. 每名 NPC 都编译完整情感引擎：伤口、未满足需要、防御、错误信念、秘密愿望、关系触发点和最终变化。
6. 关系是主要推进引擎；线索改变局面，关系让改变产生代价。
7. 每章都有完整起承转合，四拍同时包含剧情功能、情绪变化、关系变化和玩家此时要回答的问题。
8. 情感可以强烈，但优先通过嘴硬、保护、尴尬、误解、旧习惯和行动代价表现，不靠持续哭喊和创伤独白。
9. `user_view` 只含开场时玩家可知内容；导演秘密不能进入简介、人物卡或初始选项。
10. 初始两个选项必须代表两种真正不同的处世方向，只能回应已经发生的内容。
11. 专业、制度、技术和权限必须有正史支撑，不再用虚构规定、断网、撤职或万能设备制造冲突。

Prompt 1 输出：公开故事视图 + 导演数据，包括人物、章节弧、玩家契约、锁定开场、事实目录、关系规则、揭示门槛、段落锚点、约束、终局条件，以及只说明“此处适合放什么”的 `experience_moments` 编辑建议。它们不包含运行触发、material绑定、URL或组件参数。

## 3. Prompt 2：运行编译与小段起承转合

输入：已确认 StoryPackage；可选的编译段落范围；完整段落顺序；完整文风配置。

本轮测试后形成的核心规则：

1. Prompt 2 只编译，不再新增人物过去或改写正史。
2. 玩家自定义身份是独立 Persona 起点；每个场景要允许 NPC 因玩家的身份和实际表现形成好奇、试探、信任、担心、佩服、不服或合作。
3. 角色决策卡包含身份职位、职责、真实权限、专业边界、公开与当下目标、防御方式、隐藏计划、保密边界、关系策略、口语节奏和失格行为。
4. 高位或专业角色必须聪明地阻拦：限定范围、提高证据门槛、重新分工、控制知情面或给出替代路径；不能靠降智、装外行和胡编规定拖戏。
5. 每个 segment 固定单一地点、在场人物、允许范围、未知问题、退出条件和禁止越界事项。
6. 不仅每章有起承转合，每个小 segment 也必须有自己的起承转合；每一拍都生成对应的 `guiding_question` 和 `choice_guidance`。
7. 推进线索前先完成必要的社交节拍；玩家不是侦查按钮，NPC 必须先与玩家建立或校准关系。
8. 前三章每章不超过 20 个成功回合，后续章节可按剧情压缩；回合预算只影响编译，不进入模型每轮输出字段。
9. 每轮最多调用一项 material、造成一个主要变化；material 同时描述事实后果、情感后果和关系后果。
10. 白名单或导演材料不等于玩家已知。事实必须先在可见事件中出现，之后才允许进入选项。
11. 可见响应协议保持最小：每轮 8—12 个事件组成一个完整场景块、恰好 2 个 action/speech 选项；不再要求模型填写版本号、地点、参与者集合、关系标签、source refs 或大段 state delta。
12. 选项可以都是说话或都是行动，必须是方向相反的简短玩家言行，而不是“左边对白、右边动作”的机械配额。
13. Prompt 2不生成可执行媒体Cue。它只把Prompt 1的 `experience_moments` 放进合适segment的 `experience_opportunities`，说明可能的图片、视频、音频、文件或互动形式及戏剧作用；不输出trigger、material绑定、asset slot、URL、组件参数和生成提示词。

Prompt 2 输出：事实与知识表、角色决策卡、段落边界、段落起承转合、社交节拍、可用材料、事实/秘密白名单、玩家契约、最小响应契约、初始 runtime state，以及不参与运行状态的 `experience_opportunities`。

## 4. Prompt 3：逐轮群聊现场

输入：当前可见 RuntimePacket、玩家本轮原话或动作、输入类型、玩家身份、最近可见事件与当前关系记忆。

本轮测试后形成的核心规则：

1. 前两个事件内必须有人具体接住玩家本轮说或做的内容，不能只换话题。
2. NPC 不只判断玩家是否正确，还要对玩家产生关系反应：好奇、试探、信任、担心、佩服、不服、戒备或合作。
3. 玩家首次公开具体身份时，不同 NPC 从能力边界和关系距离两个方向自然校准态度；之后根据玩家真实表现累积，不反复念职业。
4. 对广为人知的现实公众人物或虚构角色，可使用稳定公共常识识别，但不能编造私生活、实时新闻、特殊权限或与 NPC 的既往关系。
5. 只使用公开事实、公开关系、最近事件、本段允许材料和在场 Persona；导演数据、未来角色和未满足揭示门槛的内容不能出现在可见文本。
6. 媒体触发前必须先写出可看见或听见的具体瞬间，再写人物反应，防止视频、图片或音乐早于剧情弹出。
7. 每句 NPC 对白内部检查身份、权限、专业、知识边界、目标、防御/隐藏计划以及当前说话对象。
8. 知道秘密不等于会说漏。知情人物可用部分真话、反问、答非所问、沉默或替代方案保护底牌。
9. 每轮输出 8—12 个连续事件；先回应玩家，再让 NPC 按自己的目标继续行动，并至少形成一项探索收益与一项关系或情感代价，最后停在真实决策点。至少两名在场 NPC 参与，但动作、沉默和回避也算参与，只要求至少一人开口。同一 NPC 可以连续说话。
10. 允许一轮只推进关系，不强迫每轮都推进案情；但至少一名 NPC 对玩家的态度应发生可感知的小变化。
11. 持续承接玩家近期态度、反常变化、未回答问题以及 NPC 对玩家的当前印象。
12. 两个选项各 8—24 字，是玩家下一步可直接提交的言行；两项必须方向相反，不能首次透露人物背景、亲属、地点、证据或结论。
13. Prompt 3 严格只输出 `{events, choices}`，不再承担状态计数和后端账本工作。
14. `experience_opportunities`只是编辑建议，Prompt 3不得把它当成已经存在的媒体、事实或触发Cue，也不得写进正文和选项。

## 5. 文风当前状态

当前文风由 `app/workflow-prompts.ts` 中两层文本规定：

- `filmGrammar`：Prompt 1/2 使用的完整创作规则；
- `turnFilmGrammar`：Prompt 3 每轮使用的短版，减少请求体和延迟。

当前规则是项目自己定义的“冷峻黑色犯罪群像影视文风”，不是 Gemini 或其他模型自带的固定文风。模型只负责按这份规则表演。

## 6. 把文风改成入参

建议新增通用 `StyleProfile`：

```ts
type StyleProfile = {
  id: string;
  name: string;
  full_directive: string;
  turn_directive: string;
  narration: string[];
  dialogue: string[];
  humor: string[];
  emotional_temperature: "restrained" | "balanced" | "intense";
  pacing: "slow" | "medium" | "fast";
  forbidden: string[];
};
```

编译接口接受以下二选一：

```json
{
  "storyId": "new-story",
  "styleProfileId": "dark-crime-ensemble"
}
```

或：

```json
{
  "storyId": "new-story",
  "styleProfile": {
    "id": "custom",
    "name": "用户自定义文风",
    "full_directive": "用于Prompt 1/2的完整要求",
    "turn_directive": "用于Prompt 3的短版要求",
    "narration": [],
    "dialogue": [],
    "humor": [],
    "emotional_temperature": "balanced",
    "pacing": "slow",
    "forbidden": []
  }
}
```

运行原则：

1. Prompt 1/2 使用 `full_directive`，把文风编译进故事与角色决策。
2. Prompt 3 只携带 `turn_directive` 和当前场景必要的少量约束，避免每轮重复发送整篇文风手册。
3. StoryPackage 保存所选 `style_profile_id` 与编译后的 style，保证长轮次一致。
4. UI 可提供预设选择，也允许粘贴自定义文风；切换文风需要重新编译 Prompt 1/2，不能在故事中途静默替换。
5. 文风只改变表达、节奏、幽默和情感浓度，不得改变剧情硬事实、知识边界、角色权限和揭示门槛。

## 7. 复用到另一个 Demo

Prompt Workflow 已经可以复用。新故事只需要提供：

- 新剧情卡；
- NPC Persona 与角色图片；
- 玩家契约；
- 章节与段落计划；
- 可选的现有媒体素材；Prompt 1/2会自行提出其他体验机会，但当前阶段不自动绑定触发；
- 文风预设或自定义 StyleProfile。

仍需从 Lotus 99 中抽离的故事专用部分：

- `workflow-source.ts` 的剧情数据；
- `workflow-precompiled.ts` 的当前预编译包；
- `chat/route.ts` 中硬编码的媒体触发定义；
- 章节结算、换装卡、论文和终局投票的 Lotus 专用配置。

下一步应把这些内容合并为独立 `StoryDefinition`，由 `storyId` 选择，而不是再复制一套 Prompt 和页面。
